### Incident: "tomorrow" reminders sent on the day, and emails showing a blank or wrong address — ✅ fixed 2026-09-23 (`b754d7b`)
- Raised by: office — 2026-09-23. Three reminders fired at 08:01 saying the appointment was "tomorrow" while showing that day's date; the appointments were that day. One also had an empty Address line.
- **Cause 1 — day-before reminders fired at 0 OR 1 days out.** That range was a deliberate catch-up for a missed run, but the word "tomorrow" is fixed text in the template. Evidence: the timer *did* run on the 22nd (it sent job #36's install week reminder), and all three appointments were booked later that day, after the single 08:00 run. First opportunity was therefore the morning of the appointment.
- **Fix**: reminders now fire only at exactly 1 day out (surveys, service calls and installs alike), **and the check runs hourly 07:00–19:00 UTC** instead of once at 07:00. The hourly run is the important half: suppressing same-day reminders on its own would have meant anything booked after 08:00 the day before got **nothing**, silently. Anything booked after the last run on the day before still gets no reminder, by design — the booking confirmation already states the date.
  - **Winter caveat**: the schedule is UTC, so once BST ends the window becomes 07:00–19:00 UK. Setting `WEBSITE_TIME_ZONE` on the Function App would pin it to UK local time year-round — small infra change, not done.
- **Cause 2 — every email read the address from the CUSTOMER.** Site addresses moved onto jobs on 2026-09-17 and customer addresses were cleared, but the eight email builders in `reminderCore.js` were never updated. Of 60 jobs: **38 emails showed a blank address, and 4 showed a DIFFERENT site** belonging to the same trade customer (all four Conservatory Renovators sites quoted "4 Earle Croft"). Now uses `job.siteAddress || customer.address`. Verified against live data.
- **General lesson**: when a field moves between record types, grep for every reader — the Customer/Opportunity migration checked the UI thoroughly but not the email templates, which are the part customers actually see.

### Tommy Trinder integration (second quoting system after WindowCAD7) — 🔍 researched 2026-09-21, not started
- Requested by: office — 2026-09-21. Launch targets WindowCAD7 users first; Tommy Trinder (tommytrinder.com) is the next quoting system to support. The office has no Tommy Trinder licence.
- **What's publicly known** (from their site, FAQ, pricing page and Business Pilot's setup guide — no public API documentation exists):
  - They advertise an **"open API — let us know what you need"** and invite custom integrations. Named CRM partners: **Business Pilot** and **Adminbase**.
  - **CRM integrations need the Grow plan or above**: Start £120/mo (no integrations), **Grow £220/mo annual / £245 monthly**, Fly! £320, Superfly! £500. No free trial.
  - Authentication is a **User ID + API Key** generated inside a Tommy Trinder account (Profile → My Profile → "… API Access").
  - The Business Pilot integration is **two-way**: customer details (name, email, postcode) go to Tommy Trinder; **net quote values** plus quote and pricing **PDFs** come back. A quote is started from a button in the CRM, and Tommy Trinder pushes results back via a webhook enabled in its settings.
- **The key difference from WindowCAD7**: WindowCAD7 has a *generic* webhook in its own settings that anyone can point at any URL, which is why that integration was built without the vendor's help. Tommy Trinder's webhook setting is labelled **"Business Pilot Webhook"** — it appears to be a named, partner-specific integration. So GlazeStream will very likely need **Tommy Trinder's cooperation** to be added as a destination, not just an API key.
- **Can't be established from public information**: whether quote **status changes** (sent / accepted / lost) are available — WindowCAD7 status is what drives our pipeline stages; whether line items or product detail are exposed; rate limits; whether a sandbox exists.
- **Worth noting for the VAT question**: Tommy Trinder sends **net** quote values; WindowCAD7 sends **VAT-inclusive** ones. Two sources with different VAT conventions landing in the same Quote Value field would make margins inconsistent between firms — the VAT decision (see the VAT entry) needs settling before a second quoting source is added.
- **Recommended route — don't buy a licence first**: approach Tommy Trinder as a prospective integration partner (they explicitly invite this) and ask for (1) API documentation, (2) a partner/developer account to build and test against, (3) whether they'll add GlazeStream as a named webhook destination like Business Pilot, and (4) whether quote status changes are sent. A licence only becomes necessary if they won't provide a test account; the Grow plan is the minimum that includes API access. In production each glazing firm would need their own Grow-or-above plan and would enter their own credentials — stored per company, which depends on the multi-tenancy work in Launch Readiness.

### "AI Integration" section — Claude/OpenAI connected to the CRM — 💡 idea, needs a decision before scoping
- Requested by: office — 2026-09-13. Two shapes proposed: (a) a new left-nav "AI Integration" section where a user brings their own existing AI subscription, useful for interrogating uploaded data ("upload a bank export and ask how much money have I made this month"); or (b) Claude embedded as a first-party GlazeStream feature.
- **Correction that changes the design of option (a)**: a ChatGPT Plus / Claude Pro **subscription does not grant API access**. They are separate products with separate billing — a consumer subscription cannot be plugged into a third-party app. Connecting either provider requires an **API key** (console.anthropic.com / platform.openai.com), billed per-token, entirely separate from any subscription the user already pays for. So "let them use the AI they already have" isn't really available; the realistic version of (a) is "let them paste in their own API key."
- **The value is data access, not a chat box.** A generic chat panel inside the CRM is worth very little — the user already has ChatGPT/Claude in another tab, and pasting CRM data into it by hand is what they'd do anyway. What no general-purpose chatbot can do is answer questions *against the live CRM*: "which quotes over £5k haven't been followed up in two weeks?", "summarise this customer's survey notes and flag anything unusual", "draft a follow-up email for this job in our house style", "which fitter is overbooked next week?". That requires the model to be able to query Customers/Jobs/Settings — i.e. a first-party build (option b), not a BYO-key chat window.
- **On the bank-export example specifically**: the CRM already knows won revenue, cost, gross profit and margin per period (Deals Won, made accurate 2026-09-12) — for "how much have I made this month" the CRM's own data is the better source. Where a bank export genuinely adds something is the gap the CRM does *not* track: **cash actually received vs quoted/won value**, plus overheads and expenses. If that's the real need, the honest answer may be a payments/reconciliation feature rather than an AI one — worth separating the two before building.
- **Hard constraints that shape any version of this**:
  - **The API key can never live in `index.html`.** It is a single static file served to the browser; anything in it is readable via View Source, and a leaked key is billable to whoever owns it. Every AI call must proxy through the Function App, with the key in Key Vault (`visualpro-crm-kv` already exists) or an app setting — same pattern as the Azure AI Speech key used by `/api/transcribe`.
  - **GDPR.** Real UK customer names, addresses, phone numbers and job details would be sent to a third-party processor. Needs a data-processing agreement with the provider and a decision on what's in scope; Anthropic's commercial terms cover this, and zero-data-retention is available, but it's a business decision to make deliberately rather than discover later.
  - **Cost is per-token, not flat.** For a single office's usage this is small (realistically a few £/month), but it is usage-billed and needs a cap/budget alert so an accident can't run up a bill.
- **ANSWERED 2026-09-13**: this is for **other businesses GlazeStream may be sold to** — the office explicitly counts their own usage in the same bucket ("ultimately we are just another GlazeStream customer"). So design for multi-tenant SaaS from the start, not for one office. **Going through a design pass before anything is built.**
- **This partly reverses the earlier BYO-key take.** Commercially BYO-key looks attractive (each tenant carries their own token costs and their own data-processing relationship), but the *audience* kills it: the buyer is a small non-technical double-glazing firm. Asking their office manager to create an Anthropic/OpenAI account, set up billing, generate an API key and paste it into a settings page is an onboarding cliff almost none of them will climb. BYO-key is at best an optional escape hatch for a large tenant who wants their own billing — never the default path.
- **Recommended model instead**: GlazeStream holds one provider key, meters token usage **per tenant**, includes a monthly allowance in the subscription and charges for overage. Tenants never see a key. Same shape as most SaaS AI features. Requires per-tenant usage accounting to exist *before* launch, not after.
- **Sequencing — the most important point.** Two existing pieces of work are hard prerequisites, not nice-to-haves:
  1. **Multi-tenancy is not implemented.** `TenantId` is reserved on Customers/Jobs but everything runs as `TenantId=1`. An AI with query tools on top of a data model that doesn't *enforce* tenant isolation turns any bug from "wrong number on a dashboard" into "Firm A asks about their pipeline and sees Firm B's customer list." Tenant isolation must be real and tested first.
  2. **The Customer/Job architecture gap** (duplicate customer records, ambiguous Customer-vs-Job semantics — see 2026-08-07) would be inherited directly by the AI's answers. **AI amplifies data-model problems**: users forgive a dashboard being slightly off, but an assistant confidently stating something false reads as a lie rather than a bug, and costs trust disproportionately.
- **Commercial risk to model with real numbers before committing**: per-token cost is variable, SaaS revenue is flat. A single heavy tenant can eat the margin on several quiet ones. Needs per-tenant caps, a tier or metered pricing, and alerting — decided up front, because retro-fitting a cap onto a feature customers already use unlimited is a painful conversation.
- **Legal chain changes shape as a product.** Not just controller-of-own-data any more: homeowner → glazing firm (**controller**) → GlazeStream (**processor**) → AI provider (**sub-processor**). That means a DPA with the AI provider *and* tenant-facing terms that disclose the sub-processor. Zero-data-retention is available and worth taking. This is a real obligation, worth a proper look during the design pass rather than after launch.
- **Prompt injection**: the AI would be reading tenant-supplied free text (customer notes, emails, uploaded PDFs). A malicious or careless string in a record can attempt to steer it. Small blast radius with read-only tools; genuinely risky once it can write, send email, or change stages — another argument for read-only first.
- **Overlaps with the pending dashboard redesign**: "what needs my attention today?" is the same underlying question both features answer. Worth designing them together rather than building two separate answers to it.
- **Suggested v1 if it goes ahead** (first-party, phased): **read-only** — a chat panel with a small fixed set of query tools over Customers/Jobs/Settings, proxied through the Function App, tenant-scoped, metered. Prove it's useful and safe before letting it draft emails, create tasks, or change stages. File upload (bank exports etc.) is a later, separate phase — storing other businesses' financial data is a significant escalation in liability and probably not v1 at all.

### ⚠️ VAT treatment of Cost is undefined — affects every margin figure in the CRM — needs an answer
- Raised 2026-09-14 while scoping the supplier-quote auto-extraction below. **Not a feature request — a possible live accuracy problem**, same category as the dashboard issues fixed 2026-09-12.
- **Revenue is stored VAT-inclusive.** WindowCAD7 populates Quote Value with "the full VAT-inclusive total, per the office's confirmed choice" (`api/src/functions/windowcad.js`). **Cost has no stated convention at all** — it's typed in by hand, and nothing in the app, the API or the docs says whether it should be inc or ex VAT. `calcMargin(value,cost)` (index.html ~L391) does a plain subtraction with no VAT awareness anywhere in the codebase.
- **Why it matters**: if the business is VAT-registered (near-certain at this revenue), input VAT on supplier invoices is **reclaimable**, so the true cost to the business is the **ex-VAT** figure. Mixing a VAT-inclusive revenue with an ex-VAT cost overstates gross profit; using inc-VAT for both leaves the margin *percentage* right but inflates the profit **£** by 20%, because the VAT collected is remitted to HMRC and was never the firm's money.
- **Needs answering before**: the supplier-quote auto-extraction (below — the office asked for the *VAT-inclusive* total to go into Product Cost, which may be the wrong figure), the dashboard margin percentage, and especially the revenue/margin **targets** feature, where "what do I walk away with" is a net-of-VAT, net-of-overheads question.
- **Questions for the design pass**: is the business VAT registered (assume yes)? Should Cost be stored ex-VAT and Revenue shown both ways? Or store both ex-VAT and display inc-VAT where a customer-facing number is needed? Whatever is chosen needs a migration decision for cost figures already entered under no stated convention — those are of unknown treatment and may be mixed.

### Limitation: WindowCAD7 only syncs to the CRM on project creation or status change, not on a plain field edit
- Raised by: office — 2026-09-03, after a Customer record named "Vicky" wasn't updated with her surname despite it being added in WindowCAD7
- **Root cause (WindowCAD7's own limitation, not a bug in our integration)**: WindowCAD7's webhook "Events" trigger list only offers "Project created," "Project status changed," and per-designer-type "submitted" events — there is no generic "field edited"/"project updated" trigger. So editing a project's Name (or any other detail) with no accompanying status change never fires a webhook at all, and the CRM correctly has nothing new to process.
- **What actually happened with Vicky's record**: captured events show two `Project_created` events (14:06–14:08) with the name still just "Vicky," then a `Project_status_changed` event at 14:45 whose payload carried the corrected name "Vicky Olariu" — which is what landed in the CRM. The surname synced as a side effect of an unrelated status change carrying the project's full current data with it, not because the name edit itself was detected. A future detail-only edit will go unsynced again until the next status change happens to sweep it up.
- **Not yet built / options if this needs to be more reliable**: (1) accept the limitation and rely on status changes eventually catching up any edits, as happened here; (2) add a manual "resync this project" action in the CRM that re-fetches the project's current data from WindowCAD7 on demand; (3) poll WindowCAD7 periodically instead of relying purely on webhooks (heavier, likely unnecessary given how rarely a detail-only edit with no status change happens in practice). - **Workflow wanted**: office generates a Survey document in WindowCAD7 (Survey → Print to PDF), uploads it to the Job's existing Survey tab (already works today) → the CRM automatically "digitises" that PDF, extracting its frame-by-frame structure (each frame's name, quoted dimensions, and the blank measurement fields WindowCAD7's template always includes) → a new "Start Survey" button appears in the fitter mobile view (Survey tab, next to/instead of the plain document link) → fitter fills in a digital version of the form on-site (real measured dimensions instead of writing on a printout), optionally by voice via a mic icon per field → completed result stays inside the CRM, attached to that Job, and the office gets an email notification when a fitter finishes.
- **Confirmed explicitly out of scope**: nothing needs to go back into WindowCAD7 itself — this is entirely self-contained within the CRM once the PDF is uploaded.
- **Why a PDF-based approach over the WindowCAD7 JSON webhook** (which already gives us the same frame data in clean structured form): deliberate strategic choice — a PDF-upload-and-digitise capability is tool-agnostic. Any quoting/CAD software that can export a PDF (most can) becomes usable this way when the CRM is eventually sold to other glazing businesses, rather than depending on each customer's specific software having its own API/webhook (which can't be assumed the way it happened to work out for WindowCAD7). The trade-off: each *different* PDF layout (from a different tool) would still need its own extraction rules taught to the system — this isn't a zero-effort universal parser, just one that doesn't require an API relationship with the source tool.
- **Built (office side)**: PDF text extraction runs entirely client-side via pdf.js — office uploads the Survey PDF to the Job's Survey tab as before, then clicks "Digitise" to extract every real fillable item (room/elevation label, quoted size, any pre-existing office comment like "Does not comply with Means of Escape"), shown as a preview list for the office to sanity-check (with a mismatch warning against the PDF's own stated item count) before confirming. Confirmed items save to `job.tabs.survey.digitised`. Verified end-to-end against two different real production survey PDFs (30 items/36 pages and 4 items/5 pages) using the real pdf.js library, not just assumed text output — the extraction initially found zero items in the browser despite passing hand-written tests, because the test fixture didn't match pdf.js's real column-based text geometry (wrapped two-line field labels have their blank value positioned *between* the label's two lines; the page header is two-column). Fixed by parsing from actual x/y text positions rather than a guessed reading order.
- **Also required a storage CORS fix**: reading a file's bytes client-side (pdf.js) needs a real `fetch()`, unlike every existing use of these blob URLs (`<a href>`, `<img src>`), which are plain browser navigation and were never subject to CORS — added a CORS rule to the storage account's blob service.
- **Built (fitter side, 2026-09-08)**: the step-through form itself — one item on screen at a time (30 items would be unusable as a single long scroll on a phone), showing the room label/quoted size/office comment for context, then 3 size-pairs, 9 dropdowns matching each field's real choice list, and one combined Trims/Comments notes field. Saves as the fitter goes (immediate for dropdown picks, debounced for typed fields), not on a final submit, since losing progress partway through a 30-item survey would be a real problem. Reuses the fitter app's existing `updateJob`/`updateJobDebounced` save pattern.
- **Also built, office's own follow-up ask same session**: a required photo per item — a dedicated photo slot (separate from the general Site Photos gallery, which isn't tied to a specific item) that hard-blocks "Mark Complete" until at least one photo is attached, confirmed as the office's explicit preference over a softer reminder.
- **Trim count requirement (refined 2026-09-08/09)**: office wants the completion email to include a total trims-needed count, broken down properly rather than a single flat number — for each item, under both the "External Make Size" and "Internal Size" fields specifically (not the top Aperture Size field), a trim picker (type + width) and an auto-calculated, read-only trim count using `⌈2×(W+H) ÷ selected trim's stock length⌉` (full perimeter, confirmed over a simpler W+H-only sum). Width and type are both **free text** (not a fixed dropdown) — deliberate choice since each future installer/customer of this CRM (once resold) will likely use a different trim supplier, so nothing should be hardcoded to Eurocell's own naming. The completion email should then group by exact width+type text and give a subtotal per group plus a grand total — flagged honestly to the office that free text only groups correctly if the same width/type wording is entered consistently across items (no dropdown enforcing that), a trade-off they accepted in favour of supplier flexibility.
- **Built (2026-09-09): Settings → Trim Catalog**, a new editable reference list (Category, Trim Name, Width, Standard Length in mm, Supplier) that will feed the per-item trim pickers above — manual add/edit/remove rows (same pattern as Fitters/Suppliers), plus a "Upload Trim List (Excel)" option that parses a spreadsheet client-side (SheetJS library, no backend change), tolerant of header-name variation, shows a preview before committing, and **appends** rather than replaces so uploading a second supplier's list later doesn't wipe out the first. Seeded with the office's real 23-SKU Eurocell price list. Each row's own stock length (not a hardcoded 5000mm constant) is what the trim-count formula above will use, so a future supplier stocking a different length works without a code change. **Not yet tested against a real uploaded spreadsheet** — the parsing code is genuinely implemented (not a placeholder), but only verified to have deployed correctly, not exercised end-to-end with a real .xlsx file yet — worth trying next session in case a real-world formatting quirk needs a fix, same pattern as the PDF extraction did.
- **Built (2026-09-10): per-item trim pickers on the fitter survey form.** Under the "External Make Size" and "Internal Size" sections of each item (not Aperture Size), a `SurveyTrimPicker`: a trim-type dropdown (distinct names from the Trim Catalog) + a width dropdown (widths that catalog stocks for that type), each with an "Other / bespoke…" option — bespoke type reveals a free-text name field, bespoke width reveals a 1–100mm number input — so the common Eurocell sizes are one tap but an unusual trim is still recordable. This superseded the earlier "both fields pure free text" plan (see the bullet above) after the office asked for quick-select common sizes with a bespoke fallback (their words: "common sizes by default but they can select bespoke if needed"). Below the pickers, a read-only auto-count: `⌈2×(W+H) ÷ stock length⌉` (full perimeter), stock length taken from the matched catalog row (or 5000mm default for a bespoke width), shown as e.g. "≈ 4 × 5000mm lengths needed". Stored on the item as `trims.makeW` / `trims.internalW` = `{type, width, bespokeType?, bespokeWidth?}`; count is always recomputed from the live catalog, not stored, so a catalog edit doesn't leave stale numbers.
- **Built (2026-09-10): survey completion → office email.** New editable **"Survey Completed → Office"** template in Settings → Email Templates (its own "Internal Notifications" group). Unlike the customer-facing templates it has an editable **recipient** (`to`, comma-separated; falls back to the General-settings Company Email if blank), an on/off toggle, and four **include** checkboxes — *Trims to order* (grouped by type + width with a total, counts recomputed server-side from the live Trim Catalog), *Per-item measurements & options*, *Surveyor notes*, *Photo count per item*. Fires server-side from `jobsUpdate` the first time `job.tabs.survey.digitised.completedAt` is set (fitter marks the last item complete), mirroring the booked-email pattern; marks `job.tabs.survey.completeEmailSent`, shown on the office Survey tab.
- **Built (2026-09-11): voice input.** Fitters use mixed iPhone/Android devices, and iOS Safari has no support at all for the browser's built-in Web Speech API — so this went straight to a proper record-and-transcribe pipeline rather than the browser API, to work identically on both platforms. A `VoiceMicButton` (tap to record, tap again to stop) captures audio via `MediaRecorder`, re-encodes it client-side to 16kHz mono 16-bit PCM WAV (sidesteps codec differences between platforms — Chrome/Android natively records webm/opus, Safari/iOS records mp4/aac), and sends it to a new `POST /api/transcribe` endpoint backed by a new **Azure AI Speech** resource (`infra/modules/speech.bicep`, S0 tier). Wired onto: the per-item **Notes** field (dictated text is appended), and each of the 6 numeric **size fields** (Aperture/Make/Internal, W and H) — a `parse` step extracts the first number said, with a clear "heard X, no number in that" error if nothing numeric was recognized, so the fitter can just retype rather than silently losing the recording. Dropdown fields deliberately **not** given voice input (tapping a short list is already fast; saying an option aloud to match a dropdown was judged the least valuable and highest-risk piece of the original scope, per a scoping conversation with the office). Kept swappable-by-design: the frontend only ever calls `apiTranscribe()`, which endpoint that calls is `transcribe.js`'s concern alone, so changing speech-to-text vendors later is a one-file change.
- **Not yet tested on a real phone** — the WAV re-encoding path (MediaRecorder → AudioContext.decodeAudioData → manual resample/PCM encode) is standard Web Audio API usage, but real iOS Safari/Android Chrome behaviour (mic permission prompts, actual recognition accuracy in a noisy site environment, background-tab suspension) can only be confirmed with a fitter's actual device — same "verify against the real thing" lesson as the PDF/Excel parsing work.

### Bug: session expiry showed a raw error, could silently lose unsaved edits — ✅ fixed 2026-09-03
- Raised by: office — 2026-09-03, after a tab left open overnight caused a Settings edit (a new feedback form question) to fail to save with a raw `PUT /settings failed: 401` alert and no clear explanation
- Root cause: session tokens last 12 hours; a tab left open longer than that keeps trying to save with a now-invalid token, and every individual save handler just alert()'d the raw technical error rather than explaining what was actually wrong.
- Fixed two ways: (1) the app now silently renews the session token every 20 minutes in the background (`POST /api/login/refresh`, works for both office and fitter logins, no password re-entry) — an actively-used tab should never actually hit this again; (2) as a safety net for when a tab really has been left long enough to miss that, any 401 now shows a clear "Your session has expired — please log in again" screen instead of a raw alert on whatever was being saved.
- Verified end-to-end: a valid token refreshes into a genuinely new working token; garbage/missing tokens are correctly still rejected (no security gap introduced).

### Customer/Opportunity model — design and decisions (approved 2026-09-17)
- Supersedes the "Extend Deal tracking" entry below, which described the same work before it was scoped. **Full design + five-phase build plan: https://claude.ai/artifact/FJJVhCrTMSz7rY6pZ7qYT9**
- **The model, confirmed by the office 2026-09-17**: one Customer record = contact wrapper only (name, email, phone, sector, source, **billing** address; no stage, no quote value). - **Zero schema migration.** `dbo.Jobs` already has every column an opportunity needs. `dbo.Customers.Stage` stays, written with a constant and never read. No manual Portal Query Editor step.
- **Scope**: 23 customer-stage reads across 11 components in `index.html`; `windowcad.js` (its `created-customer` path must create Customer *and* Opportunity; `updated-customer` retires) and `customers.js`. `reminderCore.js`/`jobs.js` substantially unaffected.

### Extend "Deal" tracking to span the whole lifecycle, not just post-Deal-Won (⬆️ superseded by the approved design above)
- Raised by: office — 2026-08-07, following directly from investigating real duplicate-looking customer records
- **The actual problem found**: querying the live database turned up several genuine trade/commercial customers with 2-3 separate Customer records each — same name, same phone, different site addresses (e.g. "Conservatory Renovators" x3: Binfield/Tilehurst/Sandhurst, all still "Followed Up"; "Adam Slark" x2: one "Quoted", one "Deal Won" with a linked Job at a different address; also "Whitman Building Services" x2 and "New Richmond Developments" x2). - **The office's confirmed direction**: "there should only ever be one customer record that is categorised by sector... it would be great to have the mini dashboard [like the existing Jobs/Active/Completed panel on Customer Directory] showing something like 3 jobs quoted, 2 jobs completed and 1 active and then the associated margin and total quoted at a glance." I.e. **retail** customers will rarely need more than one deal, but **trade/commercial** customers routinely have multiple simultaneous quotes and jobs, and the app should support that from first contact, not just after winning.
- **What this actually means architecturally**: extend the "Job" concept backward to cover the *entire* lifecycle (Prospect List → New Enquiry → ... → Deal Won → Book Survey → ... → Job Completed) as one continuous record type, rather than splitting "pre-Deal-Won lives on Customer" / "post-Deal-Won lives on Job" the way it does today. Customer becomes purely the contact/sector wrapper (name, email, phone, address, sector) that any number of these lifecycle records link to. This is comparable in size to (or bigger than) the original Customer/Job content-divergence fix built 2026-07-23 — touches the Sales Pipeline Kanban/stage model, Dashboard reporting, Customer Directory's mini-stats panel, `handleDealWon`, the New Enquiry/website-lead-capture flow, and needs a real migration plan for the existing duplicate records found above so none of their history/stage/quote data is lost.
- **Do not start this without a proper planning pass** (research the current data model + a design proposal, same approach as the original Customer/Job unification work) — too large and too close to real production data to improvise.

### WindowCAD7 CRM integration — ✅ built 2026-08-19
- Requested by: office — 2026-08-11, response from ICAAL received 2026-08-19
- ICAAL provided no formal API docs, just pointed at WindowCAD7's own Settings → CRM panel — discovered it's a webhook: WindowCAD7 POSTs a project's JSON to a URL of our choosing whenever a chosen event fires ("Project created" / "Project status changed" / others). Built a receiver (`POST /api/windowcad/webhook/{secret}`, secret-in-path since WindowCAD7 only offers a plain URL field, no custom headers) that:
  - Always captures the raw payload (viewable in-app at Settings → WindowCAD7) so future payload shapes can be inspected without needing a new build.
  - Matches an incoming project to the CRM: already-linked by WindowCAD7 Reference → update in place; else an existing customer found by email or phone → new Job created under them (repeat/concurrent business, using the CRM's existing multi-Job-per-Customer support); else → new Sales Pipeline lead created, stage set to "Quoted" if a price already exists.
  - Auto-populates Name, Email, Phone, Address+Postcode, Quote Value (WindowCAD7's VAT-inclusive total), and Installation Value (parsed from WindowCAD7's free-text Installation Fee field, confirmed always in a fixed format) — Product/Installation **Cost** stay manual, WindowCAD7 has no concept of internal cost.
  - Shows WindowCAD7's own project status as a clearly-labelled read-only line — deliberately does **not** drive the CRM's own Sales/Install pipeline stage, the two vocabularies don't correspond.
  - The CRM now also quietly refreshes customer/job data every 20s while logged in, so a WindowCAD7 update shows up without a manual page reload.
- Verified fully end-to-end against real WindowCAD7 test data (a real project created and auto-populated a new lead correctly; a real price/status change updated that same lead's Quote Value and Status).
- **Real bug found and fixed same day**: WindowCAD7 sometimes sends its webhook with `Content-Type: text/plain` even though the body is genuinely JSON — the receiver originally trusted that header and silently discarded the event as an opaque raw-text capture instead of processing it. Fixed to always attempt `JSON.parse` on the raw body regardless of the declared content type.
- **Second real bug found and fixed same day**: shortly after the fix above, a linked test customer's record regressed to an older price/status with no corresponding new webhook event in the captured audit trail — root cause not fully pinned down, but fixed regardless: WindowCAD7 includes its own `modifiedDate` on every payload, now stored as `windowcadModifiedAt` and checked before every update, so an update whose `modifiedDate` isn't newer than what's already stored is skipped rather than applied. Verified by deliberately replaying an old event afterward and confirming it was correctly rejected (`"skipped-stale"`).
- **Not yet tested**: WindowCAD7's separate "Print to CRM" button / "Print document" option (seen in its CRM settings, currently off) — looks like it may send an actual generated document (e.g. the quote PDF) rather than JSON, which could enable auto-attaching the Quote/Survey/Order Confirmation documents the office currently attaches by hand. The receiver was made defensive about non-JSON bodies in anticipation of testing this next.

### Incident: WindowCAD7 webhook silently broken 2026-09-10 → 2026-09-12 (self-inflicted, fixed) + matching upgraded to survive Reference renames — ✅ fixed 2026-09-12
- Raised by: office — 2026-09-12, "only some [WindowCAD7] quotes are coming through and the values don't seem to be coming across"
- **Root cause, found by cross-referencing every captured webhook event against the office's real WindowCAD7 project list**: fixing an unrelated login outage on 2026-09-10 involved linking the Function App as the Static Web App's backend, which — as a side effect — locked the Function App down to accept traffic only via the Static Web App. WindowCAD7's webhook calls the Function App's direct `azurewebsites.net` URL (configured once in WindowCAD7's own Settings → CRM, entirely independent of the CRM's own frontend), so every single webhook WindowCAD7 sent from that point on was rejected outright (`401`, at the network level, before the receiver's own code ever ran) — not a partial/intermittent problem, complete silence for ~36 hours. Confirmed by curling the direct URL directly (401) vs the same route through `crm.glazestream.co.uk` (200, applied correctly). **Fix**: office updated the URL configured in WindowCAD7 to the `crm.glazestream.co.uk/api/windowcad/webhook/{secret}` form instead of the direct Function App address — no CRM-side code or infra change needed, one field in WindowCAD7. Confirmed working end-to-end immediately after (office edited 3 real projects, all 3 landed correctly within the same minute).
- **Also found while reconciling, separate from the outage**: (1) a project's **Reference can be renamed** in WindowCAD7 after the CRM has already linked to the old value — since matching was purely by Reference text, this silently broke the link and caused the next webhook to create a **duplicate** CRM record instead of updating the existing one (real example: "Forrest Builders", Reference renamed `"Lock Avenue Option 1"` → `"Lock Avenue - All Options"`, second customer record created). (2) **Two different real WindowCAD7 projects sharing one Reference** (e.g. "Option A"/"Option B" quotes for the same address) collide into a single CRM record — whichever has the more recent `modifiedDate` wins, the other's status/price is invisible in the CRM, by design of the staleness guard but not obviously by design of the matching itself.
- **Fixed**: `extractProjectFields` now also captures WindowCAD7's own permanent internal `project.id` (`windowcadProjectId`) — unlike Reference, this never changes even if the office renames the project later, and it's genuinely unique per project even when two projects share a Reference (confirmed directly from the captured event log: "Lock Avenue Option 1"/"Lock Avenue - All Options" resolved to the *same* id, confirming it was one renamed project; "55 Worsley Road"'s two Options resolved to two *different* ids, confirming they're genuinely separate projects). `applyWindowcadProject`'s matching order is now: (1) match by `windowcadProjectId` if the record already has one stored — robust, survives Reference renames, correctly tells apart same-Reference projects; (2) fall back to the old Reference-text match **only** for a record that has never been touched under the new system (no `windowcadProjectId` stored yet) — a one-time legacy path that stamps the id on first touch, after which that record is matched by id from then on; (3)/(4) unchanged (match by email/phone, else create new lead). This doesn't retroactively fix already-collided historical data, but the same class of problem won't recur going forward for any record that gets touched again.
- **Manual cleanup done same day**: deleted the stale, empty duplicate "Forrest Builders" customer record (the one still linked to the old renamed Reference) now that the real one has the correct £15,187.20 quote.

### Incident: WindowCAD7 status/price updates silently discarded by the staleness guard — ✅ fixed 2026-09-14
- Raised by: office — 2026-09-14, "why have the values not come across from WindowCAD for this record" (Knights Property Services showing WindowCAD7 Status "Enquiry" and a blank Quote, when WindowCAD7 had it at "Quotation Sent").
- **Root cause: WindowCAD7 does not reliably bump a project's `modifiedDate` when its status or price changes.** All four events for Knights carried the identical `modifiedDate` (`2026-09-14T12:14:47.362Z`, equal to its `createdDate`) while the payload went Enquiry/£0 → Quotation Sent/£60 → Quotation Sent/£58.20. The staleness guard added 2026-08-19 (`api/src/functions/windowcad.js`) skipped any event whose `modifiedDate` was `<=` the stored one — so the first event applied, and **every genuine update after it was rejected as stale**.
- **Systemic, not a one-off**: across the 50 captured events, **6 of the 14 projects with more than one event** had a frozen `modifiedDate` despite a real status/price change — including £37,950, £18,960 and £13,548 jobs. The other 8 projects *did* get a moving `modifiedDate`, which is why this presented as intermittent ("only some are coming through") rather than obviously broken.
- **Fix**: `<=` → `<`, so only **strictly older** events are rejected. An equal `modifiedDate` now means "WindowCAD7 didn't bump it", not "nothing changed", and the later-arriving event wins. Duplicate redelivery just re-applies identical values (harmless); genuinely out-of-order older events are still blocked, which is what the guard was for.
- **Backfill — deliberately only one record.** The plan was to replay the latest captured event for all 6 affected projects, but checking the data first showed **5 of the 6 already held the correct quote value**; what they had was a possibly-stale status *label*, and for four of them the most recently *received* event carried an earlier-sounding status than what was stored (a side effect of the 2026-09-12 reconciliation re-triggering projects out of order — with `modifiedDate` frozen, arrival order is not reliable chronology). Replaying those would have pushed good records backwards to fix a cosmetic label. Only **Knights (#77)** had genuinely missing data; its event was replayed through the real webhook and it now reads Quotation Sent / £58.20 product + £90.00 installation = £148.20. The other five self-heal on their next real event now the guard is fixed.
- **General lesson**: a guard that depends on a third party maintaining a field correctly needs to fail *open* on ambiguity, not closed. Rejecting a real update is worse than re-applying a duplicate, because the rejection is silent and the office just sees a blank field with no error anywhere.
